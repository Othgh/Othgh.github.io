DASCTF NewStar「雪梨」— phar 反序列化 + __wakeup 绕过

目标：http://41114b5a3e35c96852c80c18.http-ctf2.dasctf.com（NewStarCTF 雪梨题）
环境：openresty 反代 → Apache2 + PHP 7.0.9，CWD = /var/www/html，运行身份 www-data
FLAG：CTF2{6e35f438-78bf-42b2-9ad3-04c7a70458b5}（文件在 /flllag，注意三个 l）

一、入口侦察

  • index.php 是个假上传页（”其实这次不是在这里上传”），但响应头下发：
    Set-Cookie: looklook=pairing.php ← 真入口提示
  • 访问 /pairing.php 即题目本体（源码见下）。响应头 X-Powered-By: PHP/7.0.9 是关键指纹。

二、源码要点

利用链：file_exists('phar://x.phar/...') → 解析 phar manifest → unserialize(metadata) → __destruct() → system($this->eating)

目标对象：user='admin'(private, 序列化名 \0story\0user)、eating=<命令>、God='true'。

三、两个坎

坎 1：__wakeup() 里的 die()

__wakeup 无条件把 user 改成 human 再 die()。
→ 用 CVE-2016-7124：序列化串里声明的属性个数 > 实际属性个数时跳过 __wakeup。
PHP 7.0.9 正好 < 7.0.10（修复版本），可用。
O:5:"story":4:{…} → O:5:"story":5:{…}（等长替换，偏移不变）

副作用：file_exists() 会报 Notice: Unexpected end of serialized data，无害，对象照样构造成功。

坎 2：urldecode($file)

body 会过 urldecode，所以必须先 urlencode(phar_bytes) 再发（urlencode/urldecode 严格互逆，二进制安全）。

四、⭐ 最大的坑：PHP 8.1+ 的 phar 签名格式（GBMB）

本机只有 PHP 8.5，用它生成 phar 时踩了两个大坑，排掉这两点才打通：

  1. PHP 8.1+ 的尾部布局是 [content][sig20][flags4][GBMB4]，比老格式多 4 字节 GBMB 魔术字。
    我一开始”好心地”把 GBMB 剥掉、按 PHP5/7 老格式 [content][sig][flags] 重建 → PHP 5.6.9 / 7.3.4 全都报 has a broken signature。
    实测结论：PHP 5.6/7.x 反而能正常读 PHP 8.5 的原生输出（含 GBMB）。所以千万别手工降级格式。

    • PHP 8.5 自己读无 GBMB 的文件 → has a broken signature（8.1+ 强制要求 GBMB）
    • PHP 5.6.9 读带 GBMB 的原生文件 → OK

  2. 签名必须重算：改一个字节（4→5）后，签名失效 → phar 直接被拒、静默不触发（file_exists 返回 false）。

六、发包

七、⚠️ 回显位置陷阱

system() 的输出出现在响应里 高亮源码 <code>…</code> 之前（PHP 输出缓冲顺序），
用 sed -n '/<\/code>/,$p' 过滤源码会把命令回显吃掉，表现为”时有时无”。
正确做法：直接在原始响应里 grep -o 'CTF2{[^}]*}'。

九、可复用的方法论

  1. 响应头/Set-Cookie 常藏入口提示（本题 looklook=pairing.php）。
  2. phar 反序列化不需要 unserialize()：任何走 phar:// 的文件函数（file_exists/file_get_contents/filesize…）都会反序列化 metadata。
  3. 本地有漏洞版 PHP 就能完整复现：本机 phpstudy 自带 PHP 5.6.9（<5.6.25，同样可用 CVE-2016-7124），对照实验一次定位问题，比盲打靶机快得多。
  4. 改 phar 字节必须重算签名（SHA1 覆盖 content），但不要改布局。
  5. PHP 7.0.9 是个甜点版本（phar 即时反序列化 + __wakeup 未修复）。
